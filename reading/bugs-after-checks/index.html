The bugs arrived after the checks

Where 76 code-review findings were born, and what we changed once we knew

76 findings. 35 of them written after every check had passed.

written
6 October 2026
about
engineering workflow · AI agents · code review
window
76 findings across five pull requests, August 2026

Our checks looked at the first commit. Almost half of what review found was written after it.

I am a Member of Technical Staff at an a16z-backed startup. We are two people shipping a command-line tool that gives founders a team of AI agents. Agents write most of the code. My co-founder reviews every pull request I open.

By August the agents were building fast, and our pull requests were still merging slowly. Across six merged pull requests, the median one needed 3.5 rounds of changes requested and 26 hours from open to merge. None of those rounds were nitpicks.

There are two easy reactions to that. Test more: rerun the full suite, add another review bot. Or test less: the checks are slow, so cut them and let review catch things. Both are arguments about how much to test. What explained our rounds was when we tested, and which commit the checks were looking at.

Five diagnoses before this one

This was our sixth diagnosis. The first five each found something true. Round one was doing requirements work after the build. My co-founder reviews every fix as if it were a new pull request. Fix commits were skipping our pre-review. Each diagnosis produced a rule, and the rounds kept coming.

None of them recorded the commit where each bug was born. Without that, a bug found in round three looks like something the first two rounds missed. Often round three had found a bug that round two's fix had just written.

Where the bugs were born

So we went back through every finding in five pull requests, 76 in all. For each one we found the first commit where the bug existed, and put it in one of three bins.

Red is what our own fixes wrote.

Thirty-five of the 76, or 46%, did not exist when our pre-review ran. Twenty-two were the same rule breaking again in a new place after a point fix. Thirteen were new bugs the fix itself created.

Twenty-nine, or 38%, were behaviour the original change never handled. Twelve, or 16%, were hygiene, like a test claim that did not match the code or a stale base branch.

Every check we had pointed at the first commit, and half the problem arrived after it. Fix commits got the least scrutiny of anything we shipped. On one pull request, 8 of the 11 blockers in round three came from fix commits that never went through pre-review.

why pre-open checks cannot see this

Even a perfect review of the first commit could have named about 42% of what review eventually found. That is the 10 findings provable at that commit, plus 22 whose shape was already visible there.

The 46% born in fix waves did not exist yet. Testing the first commit harder does not find a bug nobody has written.

Fifteen of the 76 were false-green tests, which passed without testing the thing they were named for. Ten of those fifteen were written during fix waves.

Try it: where was this bug born?

One rule, four rounds

Our tool asks founders to approve steps that cost money, and they approve by pressing Enter. The rule is that Enter must never approve something the founder cannot see.

Every fix was correct for the case named in the review, and every fix was mine. Each one left the rule broken one caller over, so my co-founder kept finding the same bug at the next door.

After round four we wrote the rule down, listed every screen where Enter can approve, and put one guard on the path they all share. Round five was an approval.

Five rules we build by

Each rule exists because one kind of round kept happening.

Check the commit under review

A pre-review of an older commit is a review of a different pull request. Every check is bound to the exact commit my co-founder opens.

Every fix is a new pull request

Review goes after the fix's own new mechanism, so we go there first. The fix's diff gets its own pre-review, and its new tests get broken on purpose to see if they fail.

Fix the class, not the leaf

When a bug comes back, stop patching the spot. Write the rule down, list every caller, and fix where they meet.

Enforce, do not check-then-act

Checking that a file is ours and then deleting it leaves a gap between the two steps. A rename that cannot overwrite, or a compare-and-swap, has no gap.

One mechanism per pull request

In August, every pull request approved in round one was small and did one thing. A money rule riding inside a cosmetic change cost a four-blocker first round.

the check-then-act story

A cleanup step checked that a file belonged to us, then deleted it. Between the check and the delete, another process could put its own file in the same place, and the cleanup would delete that one.

The first fix added a better check. The gap was still there, and review found it again. The next fix moved the file with a rename that could overwrite, which left a smaller gap. That arc took three rounds.

The next arc with the same shape went straight to an operation that cannot overwrite, and closed in one round.

The loop

This is how a change moves now. Tap through it one step at a time.

Two parts carry most of the weight. Pre-review runs again on every fix, as well as on the first commit. And a guard refuses to request review unless the pre-review ran on the commit at the head of the branch, with CI green.

The finding log

The loop gets better because of one small file with one row per review finding.

Start

76 findings, sorted by hand. Each row has the round, the severity, the commit where the bug was born, and whether our pre-review named it.

After every merge

One new row per finding. A short script turns the log into a rounds table, so the next retro starts from a query.

Before the next pull request

Every miss becomes a question on the pre-review checklist. The first pass added four. List every screen the founder sees. Ask what happens if two things happen in the other order. Break the code and check that the new test fails. Check that the pull request description still matches the code.

What changed

The 58% comes from one day and 24 findings. I would read it as a direction.

why 26%, and not 13%

Across all 61 findings in the earlier sample, Codex had named 13%. One pull request in that sample was never pre-reviewed at the right commit. Leave it out and the figure is 26%. I used the cautious number.

What it still misses

Screens and timing

Bugs on screens the founder sees, and bugs that depend on what happens first, still get through. Those need the code running, and pre-review only reads it.

Long seams

Some pull requests still ran 7 to 11 rounds. The worst kept returning to the same seam with no written list of what the pull request covered and what it left out.

Rounds are hard to count

Our round-counting script only saw formal GitHub reviews. Once verdicts started arriving as comments, a pull request with eight rounds showed up as zero. Check what your script counts before you trust its number.

Explanations that did not survive the data

tap each one

What I would copy

If you take one thing from this, add one column to wherever you track review findings: the commit where the bug was born. With that column, the next retro is a query.

Then point your checks at the commit your reviewer will open, and run them again on every fix after it. That is where 46% of our review findings came from.

Numbers come from our own review log: 76 findings across five pull requests, plus six merged pull requests for timing, August 2026. The sketches are drawn with rough.js.
