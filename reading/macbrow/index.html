Talk to your Mac in 300 ms

A read of timpratim/macbrow (github.com/timpratim/macbrow), an experimental prototype by Pratim Bhosale. Not my project; I read the code to learn how I’d build with Jev. Latencies are the author’s numbers from the README.

the code owns the menu, Jev picks from it

Nothing is generated except the text to type.

Read the code of macbrow, a voice assistant for the Mac that never hands your sentence to a big model. Your words go to Jev as a multiple-choice question over a menu of about 30 buttons; the code presses the winner. Eight diagrams, plain words first, code names in the footnotes.

TL;DR

Your Mac has a menu. Jev only ever picks from it.

Say “turn the volume up” and the program does not send that sentence to a chat model and wait. It asks Jev one multiple-choice question over the buttons it already knows how to press. Jev scores every button in about 300 ms. The code presses the winner. Everything else in the repo is plumbing around that one move.

You talk. The code picks a button. Jev scores the buttons.

Start with the picture. On the left, what you said. In the middle, a menu of buttons the code already knows: set the volume, open an app, make a note, open a website. Jev gives every button a score at the same time. The winner is pressed. A chat model is never called.

The word for that menu in the code is a tool registry, and each button is a tool: a name, a one-line description, the blanks it needs, and a tiny script. Thirty-two of them ship in a JSON file. Jev is asked one question over that list. In the SDK that question is called a Choice.

Sure, unsure, dangerous.

The score is a number, and that is the point. Sure means the code just runs the button. Unsure means the top two are close, so the Mac asks “Did you want Notes or Reminders?” Dangerous means the button touches files, the trash, passwords, or the shell; the Mac reads the action back and waits for you to say yes.

The code calls the unsure line a confidence threshold and the dangerous flag risky. There are only two states in the whole program: waiting for a command, and waiting for your yes.

The blanks get filled in the same breath.

“Turn the volume up” carries two questions: which button, and louder or quieter. Both go to Jev in one envelope. Jev answers both. The code reads only the winner’s settings and throws the rest away. When a blank is free text, like “open github dot com”, Jev does not type the answer. It points at which words of your sentence are the answer, and the code cleans “dot” into a period.

The code calls these speculative arguments: every setting of every candidate button is asked up front, so there is no second round trip. The free-text trick is span selection.

When nothing on the menu fits, it writes a new button.

“Make my screen grayscale.” No button for that. Now, and only now, a normal language model is asked to write a small script. The script has to pass six checks: can it be read, is it possible on a Mac, is it allowed, does it compile, does it actually do anything, and would a judge say it does the job. That judge is Jev again, answering yes or no with a number. If it passes, it is saved as a new button and the Mac asks “I wrote a new action to make the screen grayscale. Should I run it?” Next time, the same request is just another button on the menu.

The slow model runs once per new idea. Up to three drafts, then it gives up and says so.

In the browser it’s the same trick, one step at a time.

“Add the best vacuum cleaner to my Amazon cart.” The code opens your own Chrome, with your logins. Each step, it turns the page into a numbered list of clickable things, asks Jev which number, clicks it, and looks again. No screenshots. A 90-second clock stops runaway tasks. When it finishes it says “Done in 4 steps.” Say “the return date should be November 4th” afterward and Jev is asked one more yes/no question: is this a follow-up? If yes, same tab, same task.

The browser part is a separate library, jev-ultrafast, driven from this code. The author measured 11 seconds for the vacuum and 3.7 seconds for the date change.

The bouncer checks three times.

There is one blocklist: apps like System Settings and Terminal, commands like sudo and rm, places like your ssh keys, moves like emptying the trash or deleting files. The same check runs three times. At the door, when the buttons load, so a button that breaks a rule never even reaches the menu. At the workshop, when a new button is written, so it is thrown away instead of saved. And at the stage, right before a button runs, with your spoken words filled in, because your words can change what a button does. In the browser, anything about card numbers, passwords or deleting an account is refused outright; cart, order and subscribe ask first.

Turn the bouncer off and the Mac announces it at startup. The author’s README says why the policy exists: an early version, asked to clean up the desktop, moved every file into a folder.

Every question Jev gets is one of two kinds.

Pick one from a list, or yes/no with a number. That is the whole toolkit. Which button. Louder or quieter. Which words are the answer. Is this a follow-up. Did they say yes. Did the new script really do the job. Ten questions, two shapes, each a few hundred milliseconds, none of them writes a sentence.

If you want to build with Jev, this is the checklist. In the SDK the two shapes are called Choice and Noul.

Why it’s fast: choose, don’t generate.

The usual computer-use loop takes a screenshot, lets a big model think, has it write out an action, and then parses that text. Seconds per turn, and the model can invent a button that is not there. This loop hands the model nothing to write. Your sentence goes in, a score per button comes out, the code presses the winner. Three hundred milliseconds, and the score is a number the code can act on.

Nothing is generated except the text to type.

What I would take from it.

Four moves, in the order I would copy them.

  1. 01

    Make the menu before the model

    Write the buttons as data: name, blanks, script, what to say after. Make sure a button runs with no model in the loop.

  2. 02

    Ask Jev one question over the menu

    Pick one. Read the scores. Decide in code what high, middle and dangerous mean for you.

  3. 03

    Ask for the blanks in the same envelope

    Every setting of every candidate, up front. For free text, have Jev point at words, never type them.

  4. 04

    Let the slow model in only through a gate

    When nothing fits, let it write a button, check it six ways, save it. It should run once per idea, not once per request.

What this is not

An experimental prototype, by the author’s own warning, that runs scripts and clicks around a browser on your machine. The timings are theirs, on their machine. The browser step set lives in a separate library I did not read. I read the code to learn the shape, not to recommend running it.
